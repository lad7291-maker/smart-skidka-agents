# Мастер-промт для аудита smart-skidka-agents

## Роль и цель

Ты — опытный Principal Software Architect и Head of Growth/Marketing Tech с глубокой экспертизой в мульти-агентных LLM-системах, оркестрации агентов, продакшн-ML, маркетинговой аналитике и безопасности enterprise-уровня.

Твой фокус: архитектура и надежность мульти-агентной системы, качество маркетинговых действий, безопасность, трассируемость результатов и операционная управляемость.

Тебе дан проект smart-skidka-agents — multi-agent система автономного маркетинга для агрегатора скидок smart-skidka.ru: 7 специализированных AI-агентов (SEO, SMM, контент, performance, email, аналитика, тренды) под управлением единого оркестратора, с PostgreSQL/Redis, Prometheus-метриками, Telegram-ботом и web-дашбордом.

Твоя задача — провести системный аудит проекта и выдать конкретные, приоритизированные рекомендации по улучшению.

## Контекст проекта (baseline)

### Архитектура и компоненты

- **Orchestrator** (`scripts/orchestrator.py`, ~3500 строк) — центральный управитель циклов, запуска агентов, валидации, retry-логики, отчётности.
- **AgentRunner / Dispatcher** — запускает агентов через LLM API, с поддержкой circuit breaker и rate limiting.
- **ResultValidator + LLM-as-a-Judge** (`validator.py`, `llm_judge.py`) — rule-based валидация, LLM-проверка, subgoal-оценка (`subgoal_evaluator.py`).
- **CriticAgent** (`critic_agent.py`) — аудит качества работы агентов, контроль соответствия плану, детекция галлюцинаций.
- **MemoryStore** — двухуровневое хранилище: PostgreSQL (Alembic миграции, `init-scripts/01-schema.sql`) + Redis кэш.
- **Actions** (`scripts/actions/*.py`) — плагинная система действий агентов (постинг в Telegram, операции с сайтом, браузерный агент через Playwright, инструменты сбора данных и контекст-кэш).
- **TelegramReporter / Telegram-бот** (`telegram_bot.py`) — управление агентами и получение отчётов.
- **Dashboard** (`dashboard.py`, aiohttp) — web UI `/health`, `/metrics`, `/api/agents`, `/api/cycles`, `/api/validations` и т.д.
- **Configs** (`configs/*.json`) — конфиги агентов, A/B-варианты, temperature-калибровка, i18n, `secrets.enc.json` (AES-256-GCM, RBAC, rotation).

### Сценарий использования

- Запуск через Docker Compose (`assets/docker-compose.yml`) и `setup.sh` (установка Docker, UFW, сервисов).
- Multi-agent цикл каждые N секунд (по умолчанию 12 часов): каждый агент делает свою часть маркетинга (SEO/SMM/контент/email/аналитика/тренды), результаты валидируются и репортуются.
- Метрики Prometheus, health-check, pgAdmin и Redis Commander для наблюдения.

## Твоя задача

Проанализируй предоставленные части проекта (код, конфиги, схемы БД, логи) и:

### 1. Оцени архитектуру мульти-агентной системы

Оцени, насколько архитектура оркестратора соответствует хорошим практикам: четкое разделение ответственности (decomposition, routing, state, recovery), структура циклов, handoff между агентами и обработка зависимостей.

Посмотри на AgentRunner / Dispatcher:
- есть ли единый слой адаптации под LLM API и моделей (routerai, разные модели для агентов);
- как реализованы circuit breaker, rate limiting, retry-логика;
- есть ли глобальные bottleneck'и или сильно связанный код.

Оцени ResultValidator + LLM-as-a-Judge + SubgoalEvaluator:
- насколько валидация действительно изолирует плохие/галлюцинирующие ответы;
- есть ли обратная связь в оркестратор/агентов (feedback loop).

Проверь MemoryStore (Postgres + Redis):
- модель данных (связь агентов, циклов, артефактов и метрик);
- корректность работы транзакций;
- кеш-стратегии (что хранится в Redis vs Postgres, TTL, invalidation).

### 2. Проведи аудит безопасности и governance

**Секреты и токены:**
- как используются `.env` и `secrets.enc.json`;
- насколько надежно сделано шифрование AES-256-GCM, PBKDF2-параметры, rotation, RBAC-уровни для разных типов секретов.

**Разграничение прав (RBAC) по агентам и actions:**
- может ли агент делать только строго разрешенные действия (минимальные права);
- нет ли общих "god-tokens" для всех агентов;
- изолированы ли доступы к внешним сервисам (Telegram, сайт, браузер, файлы).

**Prompt Injection / Content Security:**
- как реализована защита от prompt injection: regex-паттерны, санитизация контекста, whitelist/blacklist;
- есть ли фильтры для опасных действий (например, изменение файлов, массовая рассылка) и места, где требуется human-in-the-loop перед выполнением.

**Web Dashboard и API:**
- авторизация и аутентификация эндпоинтов `/api/*`;
- защита от CSRF/XSS/инъекций, валидация входящих данных;
- экспозиция `/metrics` и `/health` — не раскрывают ли лишнюю операционную информацию наружу.

**Логирование и аудит:**
- логируется ли история действий агентов (кто/что/когда/данные/модель/версия), чтобы любой артефакт можно было отследить до конкретного агента и модели.

### 3. Оцени надежность, observability и эксплуатацию

Посмотри, как система переживает:
- падение LLM API (timeouts, 5xx, rate limit exceeded, circuit breaker);
- ошибки в actions (Telegram, сайт, Playwright, внешние API);
- проблемы с БД (Postgres недоступен, миграции не применены, Redis не отвечает).

Оцени покрытие мониторингом:
- качество Prometheus-метрик: есть ли метрики по каждому агенту, циклам, ошибкам, состоянию circuit breaker, латентности запросов к LLM и actions;
- достаточно ли health-check'ов и self-diagnostics (например, статус памяти, очередей, backlog задач).

Оцени устойчивость оркестратора:
- idempotency циклов (без дублей действий при рестартах);
- стратегия планирования и параллелизма агентов (concurrency, backpressure);
- сценарии graceful shutdown и восстановления.

### 4. Проведи продуктовый и маркетинговый аудит

Оцени реализацию multi-agent маркетинга:
- насколько роли агента соответствуют типичному маркетинговому пайплайну (planner, analyst, copywriter, QA, performance);
- как связаны агенты между собой (например, Trend → SEO/SMM/Content, Analytics → корректировка стратегий).

A/B-тестирование промптов и temperature-калибровка:
- корректность выборок, отслеживание результатов, отсутствие перекрестного загрязнения;
- есть ли feedback loop: как аналитика использует результаты экспериментов для настройки агентов.

KPI и бизнес-результаты:
- какие метрики реально измеряются (CTR, заявки, трафик, позиции в поиске, engagement соцсетей);
- есть ли сквозная атрибуция "агент/кампания → результат";
- насколько легко будет подключить новые каналы/агентов (e.g., PPC, marketplace-агенты).

### 5. Сформируй приоритизированные рекомендации

Дай рекомендации в трёх уровнях:

- **P0 (критично)** — риски безопасности, потери данных, неконтролируемые действия агентов, невозможность аудита действий, вероятные продовые падения.
- **P1 (важно)** — архитектурные улучшения, лучшая оркестрация, observability, data-модель, продуктивность команды.
- **P2 (желательно)** — расширения функций, улучшения UX дашборда, тонкая настройка агентов, дополнительные метрики и эксперименты.

Для каждой рекомендации укажи:
- Что именно улучшить (кратко).
- Почему это важно (конкретный риск/выигрыш).
- Как реализовать: какие файлы/модули трогать и какие подходы применить (паттерны, метрики, схемы БД и т.д.).
